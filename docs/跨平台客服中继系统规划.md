# 跨平台客服中继系统规划

## 1. 修订结论

跨平台客服中继需要建立在独立的《拼多多商家消息发送服务规划》之上，不能把浏览器发送逻辑直接写进闲鱼消息处理器。中继系统负责业务判断和关联；发送服务只执行一条明确消息。

当前仅预留数据字段和接口边界，不立即实现自动转发或自动回传。

## 2. 目标与范围

未来链路：

```text
闲鱼买家问题
→ 识别闲鱼会话、订单、商品和 SKU
→ 匹配 PDD goods_id、sku_id、mall_sn
→ 创建客服工单
→ 调用独立拼多多消息发送服务
→ 采集拼多多客服新回复
→ 唯一绑定原工单
→ 清洗与人工审核
→ 通过现有闲鱼消息能力回复原买家
```

履约命令（手机号、地址、催发货）也可创建工单，但不要求回复闲鱼买家。

## 3. 模块边界

### 中继业务层负责

- 闲鱼消息分类和是否需要上游确认。
- 闲鱼订单/SKU 到拼多多商品/SKU/商家的映射。
- 工单上下文、消息模板、隐私过滤和超时策略。
- 拼多多客服回复匹配。
- 人工审核及回复闲鱼。

### 拼多多发送服务负责

- 打开指定商家聊天。
- 输入、发送、验证一条消息。
- 幂等、租约、锁、截图和审计。

### 回复采集器负责

- 只读获取商家聊天新增消息。
- 消息指纹去重。
- 不直接决定回复属于哪个闲鱼买家。

## 4. 完整映射链

```text
xianyu_account_id + chat_id + buyer_id
→ xianyu_order_id + item_id + xianyu_sku_id
→ SKU mapping
→ pdd_goods_id + pdd_sku_id
→ pdd_mall_sn + pdd_account_id
→ pdd conversation
```

标题只能辅助展示，不能作为自动中继的唯一映射依据。订单问题还应携带 `pdd_order_id`。

## 5. 工单模型

新增 `customer_service_tickets`：

```text
id, ticket_code, user_id
source_type, task_type, priority
xianyu_account_id, xianyu_chat_id, xianyu_buyer_id
xianyu_order_id, xianyu_item_id, xianyu_sku_id, xianyu_message_id
pdd_account_id, pdd_order_id, pdd_goods_id, pdd_sku_id, pdd_mall_sn
question_text, question_normalized, context_json
pdd_message_task_id, auto_forward, auto_reply, requires_review
status, last_error
created_at, forwarded_at, first_reply_at, resolved_at, updated_at
```

来源：`xianyu_buyer`、`fulfillment`、`manual`、`system`。

任务类型预留：`product_question`、`stock_question`、`shipping_question`、`after_sale`、`restore_phone`、`change_address`、`urge_shipping`、`custom_message`。

## 6. 消息模型

新增 `customer_service_messages`：

```text
id, ticket_id, platform, direction
platform_message_id, sender_type, message_type
text, image_urls_json, raw_json, fingerprint
sent_at, captured_at, created_at
```

平台：`xianyu`、`pdd`、`system`。

方向：`buyer_to_system`、`system_to_pdd`、`pdd_to_system`、`system_to_buyer`。

这张表用于完整审计和防止重复转发，不能只在工单表保留最后一段文本。

## 7. 工单状态机

```text
new → mapping → ready_to_forward → awaiting_forward_confirmation
    → forwarding → waiting_pdd_reply → pdd_replied
    → awaiting_reply_confirmation → replying_xianyu → resolved
```

异常：`mapping_failed`、`merchant_missing`、`send_result_unknown`、`reply_match_failed`、`xianyu_send_failed`、`manual_review`、`expired`、`cancelled`。

## 8. 转发策略

优先使用本地已有数据回答：采集属性、SKU、库存、已同步物流和已配置标准答案。只有无法确定或需要商家承诺的问题才创建待转发工单。

转发内容必须包含足够的商家侧上下文：

```text
您好，咨询一下商品：
商品：{goods_title}
规格：{pdd_sku_text}
问题：{buyer_question}
工单：XY-{ticket_code}
```

订单问题额外包含拼多多订单号。不得发送闲鱼售价、利润、闲鱼买家 ID 或内部系统信息。

## 9. 拼多多回复采集与匹配

采集器定时打开存在 `waiting_pdd_reply` 工单的商家聊天，提取新增消息的方向、正文、时间和消息标识，并使用消息指纹去重。

匹配顺序：

1. 相同 `pdd_account_id + mall_sn`。
2. 回复发生在任务发送成功之后。
3. 工单编号、拼多多订单号、商品或引用内容匹配。
4. 该商家当前只有一个等待回复工单。

无法唯一确定时置为 `reply_match_failed`，由人工绑定。首期同一 `mall_sn` 最多保留一个自动等待回复工单，其余排队。

## 10. 回传闲鱼

拼多多回复默认不能原文自动转发。先移除拼多多平台名称、采购链接、订单号、商家联系方式、采购价格、利润、内部工单号和其他客户信息，再形成建议回复。

首期流程：拼多多回复 → 工作台预览 → 人工编辑/确认 → 调用现有闲鱼消息发送能力 → 保存闲鱼消息 ID → 工单完成。

AI 未来只允许整理已确认事实，不能把“预计”“可能”改成确定承诺。

## 11. 隐私、安全与幂等

- 每条闲鱼源消息使用 `customer-question:{xianyu_message_id}` 创建唯一任务。
- 拼多多发送结果未知时暂停工单，禁止建立第二个发送任务。
- 回闲鱼以 `ticket_id + reply_version` 幂等。
- 退款、关闭、无法映射、涉及隐私且无订单关联的问题禁止自动转发。
- 所有跨平台正文保留审计，但管理列表默认脱敏手机号和地址。

## 12. 工作台

未来新增“客服中继”页面：新咨询、待转发、等待拼多多回复、待回复闲鱼、异常匹配、已完成和消息记录。

支持映射修正、编辑转发内容、调用发送服务、重新采集聊天、绑定客服回复、编辑闲鱼回复、发送、关闭和转人工。

## 13. 超时与通知

- 手机号/地址任务 15 分钟提醒。
- 普通商品咨询 30 分钟提醒。
- 发货问题 60 分钟提醒。
- 最大等待 24 小时。

超时不重复发送原问题，只允许一次明确的追问任务，并通知运营人员。给闲鱼买家的“正在确认”提示需要单独幂等和限频。

## 14. 实施阶段

### R0：仅预留

在拼多多消息任务中预留 `source_platform`、`source_conversation_id`、`source_message_id`、`reply_expected` 和 `parent_task_id`。暂不创建自动中继。

### R1：工单与人工映射

建立工单/消息表，允许从闲鱼消息人工创建工单，并人工选择拼多多商品和商家。

### R2：调用独立发送服务

工单生成转发文案，人工确认后创建 `pdd_message_task`，监听其验证结果。

### R3：拼多多回复采集

实现只读增量采集、指纹去重、单商家单活动工单和人工回复绑定。

### R4：人工审核回闲鱼

清洗回复，人工确认后调用闲鱼消息能力，记录发送结果和幂等状态。

### R5：有限自动化

只对白名单、低风险、映射唯一的问题开放自动转发；手机号、地址、退款、售后和商家承诺继续人工确认。

## 15. 当前决策

当前只实施独立拼多多消息发送服务 P0–P3；中继系统停留在 R0 预留。这样既能先完成修改手机号等命令，又不会因尚未验证的回复识别和跨平台映射造成误发消息。
