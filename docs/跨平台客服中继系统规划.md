# 跨平台客服中继系统规划

> 修订状态（2026-08-20）：拼多多消息发送服务 P0～P3 和中继 R0 字段预留已经完成；拼多多会话登记、HTTP 响应捕获、消息落库及 Titan 唤醒监听已经具备代码基础，属于 R3A“待真实消息闭环验证”状态。工单、回复匹配、人工审核回传闲鱼和自动中继尚未实现。

## 1. 修订结论

跨平台客服中继建立在独立的《拼多多商家消息发送服务规划》之上。浏览器发送和采集能力不能直接写进闲鱼消息处理器：中继系统负责业务判断、关联和审核；发送服务只执行一条明确消息；回复采集器只保存平台事实。

现阶段不启用自动转发或自动回传。下一步先用真实商家回复验证“发送 → Titan 唤醒 → HTTP 捕获 → 消息去重落库”的闭环，再建设工单系统。

## 3. 目标与范围

```text
闲鱼买家问题
→ 识别闲鱼会话、订单、商品和 SKU
→ 匹配 PDD goods_id、sku_id、mall_sn
→ 创建客服工单
→ 人工确认后调用拼多多消息发送服务
→ Titan 提示商家会话可能有更新
→ 通过聊天 HTTP 数据提取新增回复
→ 唯一绑定原工单
→ 清洗、人工编辑和确认
→ 通过现有闲鱼消息能力回复原买家
```

履约命令（手机号、地址、催发货）也可以创建工单，但不要求回复闲鱼买家。退款、售后、价格承诺和隐私信息默认必须人工处理。

## 4. 模块边界

### 中继业务层

- 判断闲鱼消息是否需要上游确认。
- 维护闲鱼订单/SKU 到拼多多商品/SKU/商家的映射。
- 管理工单上下文、转发模板、隐私过滤和超时策略。
- 唯一匹配拼多多客服回复。
- 管理回复草稿、人工审核和闲鱼回传。

### 拼多多发送服务

- 打开指定商家聊天，输入、发送和验证一条确定消息。
- 提供幂等、租约、商家锁、截图和审计。
- 返回发送任务和平台消息锚点，不判断客服业务语义。

### 回复采集器

- 登记并刷新拼多多商家会话。
- 监听 Titan 事件作为刷新提示。
- 从聊天 HTTP 数据只读提取新增消息并去重。
- 不直接决定回复属于哪个闲鱼买家。

## 5. 完整映射链

```text
xianyu_account_id + chat_id + buyer_id
→ xianyu_order_id + item_id + xianyu_sku_id
→ SKU mapping
→ pdd_goods_id + pdd_sku_id
→ pdd_mall_sn + pdd_account_id
→ pdd_chat_conversation
→ customer_service_ticket
```

标题只能辅助展示，不能作为唯一依据。订单问题还应携带 `pdd_order_id`。映射缺失、歧义或来源 SKU 已失效时只能进入人工修正。

## 6. 现有拼多多消息存储

现有表继续作为拼多多平台事实来源，避免在工单层重复保存完整原文。

### `pdd_chat_conversations`

保存 `pdd_account_id + mall_sn` 对应的长期商家会话，以及 `mall_id`、`goods_id`、`pdd_order_id`、聊天页地址、最后消息、最后同步时间和 Titan 唤醒时间。

一个商家会话可以先后承载多个工单，但首期最多只能有一个等待商家回复的活动工单。

### `pdd_chat_messages`

保存平台消息 ID、方向、消息类型、正文、平台时间和原始 JSON，是拼多多消息的唯一事实来源。

### `pdd_chat_captures`

保存捕获端点及原始响应，用于解析回溯。原始响应可能体积较大且包含敏感信息，默认建议保留 7～14 天；解析后的会话消息长期保留。

```text

```

来源：`xianyu_buyer`、`fulfillment`、`manual`、`system`。

任务类型：`product_question`、`stock_question`、`shipping_question`、`after_sale`、`restore_phone`、`change_address`、`urge_shipping`、`custom_message`。

## 8. 中继消息与回复版本

新增 `customer_service_messages`，只保存工单内的引用和处理过程：

```text
id, ticket_id, platform, direction
source_record_id, source_conversation_id, platform_message_id
sender_type, message_type
normalized_text, reviewed_text, image_urls_json
fingerprint, delivery_status
sent_at, captured_at, created_at
```

平台：`xianyu`、`pdd`、`system`。方向：`buyer_to_system`、`system_to_pdd`、`pdd_to_system`、`system_to_buyer`。

回复版本字段：

```text
reply_version, reply_draft
reply_reviewed_by, reply_reviewed_at
xianyu_send_idempotency_key
xianyu_sent_message_id, xianyu_sent_at
```

闲鱼回传幂等键为 `relay-reply:{ticket_id}:{reply_version}`。编辑后版本递增，已成功发送的版本禁止重复发送。

## 9. 状态模型

业务状态与平台执行状态分开，避免一个发送失败把整个工单状态机锁死。

```text
ticket_status:
new → mapping → active → waiting_reply → review → resolved
异常：manual_review / expired / cancelled

forward_status:
pending → awaiting_confirmation → sending → verified
异常：unknown / failed / cancelled

reply_status:
none → captured → matched → reviewed → sent
异常：ambiguous / failed
```

拼多多发送任务仍使用自己的状态、租约和商家锁；工单只保存任务引用和归纳状态。

## 10. 转发策略

优先使用采集商品属性、SKU、库存、已同步物流和标准答案。只有无法确定或需要商家确认的问题才建立待转发工单。

```text
您好，咨询一下商品：
商品：{goods_title}
规格：{pdd_sku_text}
问题：{buyer_question}
工单：XY-{ticket_code}
```

订单问题额外包含拼多多订单号。不得发送闲鱼售价、利润、闲鱼买家 ID、内部账号 ID 或无关客户信息。

## 11. Titan 与增量采集

Titan 只作为“会话可能有新事件”的唤醒信号，不作为稳定的消息正文接口：

```text
Titan 收到事件
→ 更新 conversation.titan_wakeup_at
→ 标记会话需要刷新
→ 调用或捕获聊天 HTTP 接口
→ 解析方向、正文、类型、平台时间和消息 ID
→ platform_message_id + fingerprint 去重
→ 写入 pdd_chat_messages
→ 尝试匹配等待回复的工单
```

会话发现分两个入口：

1. 发送任务打开聊天页后自动登记商家会话——首期主入口。
2. 浏览器同步拼多多消息列表，发现历史或外部产生的会话——放在 R3B。

首次实测必须确认 Titan 是否触发、HTTP 捕获端点是否稳定、收发方向是否正确，以及重复刷新是否只保存一次。

## 12. 拼多多回复匹配

匹配顺序：

1. `pdd_account_id + pdd_conversation_id` 一致。
2. 回复发生在发送锚点和回复窗口之后。
3. 当前会话只有一个等待回复的活动工单。
4. 工单短码、拼多多订单号、商品、规格或引用内容匹配。
5. 结合 `last_scanned_message_id` 排除工单开始前的历史消息。

匹配后记录 `matched_pdd_message_id`、`match_method` 和 `match_confidence`。无法唯一确定时设为 `ambiguous`，由人工绑定；禁止凭列表第一条或标题相似度自动绑定。

## 13. 回传闲鱼

拼多多回复默认不能原文自动转发。先移除拼多多平台名称、采购链接、订单号、商家联系方式、采购价格、利润、内部工单号和其他客户信息，再形成建议回复。

```text
拼多多回复
→ 工作台显示原文和来源
→ 生成脱敏草稿
→ 人工编辑/确认
→ 使用版本幂等键调用闲鱼消息能力
→ 保存闲鱼消息 ID
→ 工单完成
```

AI 未来只允许整理已确认事实，不能把“预计”“可能”改成确定承诺。

## 14. 隐私、安全与幂等

- 每条闲鱼源消息以 `customer-question:{xianyu_message_id}` 唯一创建工单。
- 拼多多发送结果未知时暂停工单，禁止建立第二个发送任务。
- 同一商家会话首期最多保留一个自动等待回复工单。
- 退款、关闭、无法映射或涉及隐私且无订单关联的问题禁止自动转发。
- 管理列表默认脱敏手机号、地址、Cookie、订单号和聊天原始响应。
- 日志禁止打印 Cookie、完整地址和完整聊天响应。
- `pdd_chat_captures` 设置保留期限；数据库备份仍包含消息事实表和工单审计。

## 15. 工作台

未来新增“客服中继”页面：新咨询、映射失败、待转发确认、等待拼多多回复、回复匹配异常、待回复闲鱼、发送失败、已完成和完整消息记录。

支持人工修正映射、编辑转发内容、创建拼多多发送任务、刷新商家聊天、绑定客服回复、编辑闲鱼回复、确认发送、关闭和转人工。

## 16. 超时、通知与可观测性

- 手机号/地址任务：15 分钟提醒。
- 普通商品咨询：30 分钟提醒。
- 发货问题：60 分钟提醒。
- 最大等待：24 小时。

超时不重复发送原问题，只允许一次明确追问。正常采集和匹配不提醒，仅对租约过期、采集连续失败、回复歧义、结果未知和回传失败通知运营人员。

记录活动工单数、平均首次回复时间、采集延迟、Titan 唤醒次数、HTTP 捕获成功率、重复消息数、匹配成功率、人工改写率和闲鱼回传失败率。

## 17. 修订后的实施阶段

### R0：中继字段预留——已完成

拼多多消息任务已预留 `source_platform`、`source_conversation_id`、`source_message_id`、`reply_expected` 和 `parent_task_id`。

### R3A：拼多多会话采集底座——代码完成，待实测

已建立会话、消息和原始捕获表；Worker 已具备 HTTP 捕获和 Titan 唤醒监听；工作台可以读取会话和消息。完成标准是跑通一次真实商家回复闭环并保存验证证据。

### R3B：稳定增量采集

验证真实接口结构，完善消息列表会话发现、游标、方向识别、消息类型、断线重连、去重、原始捕获保留和连续失败告警。

### R1：工单与人工映射

建立工单和中继消息表，允许从闲鱼消息人工创建工单，人工选择拼多多商品、SKU 和商家会话。

### R2：工单调用独立发送服务

根据工单生成脱敏转发文案，人工确认后创建 `pdd_message_task`，保存发送锚点并监听验证结果。

### R3C：回复与工单匹配

实现回复窗口、单会话单活动工单、发送锚点匹配、置信度和人工绑定。

### R4：人工审核回闲鱼

生成脱敏回复草稿，人工确认后以版本幂等键调用闲鱼消息能力，记录消息 ID 和发送结果。

### R5：有限自动化

只对白名单、低风险、映射唯一且经过历史验证的问题开放自动转发。手机号、地址、退款、售后、价格和时效承诺继续人工确认。

## 18. 下一验收点

先完成真实闭环，不直接进入自动中继：

```text
人工创建并确认一条拼多多消息任务
→ Worker 打开商家聊天并发送
→ 商家产生一条真实回复
→ Titan 触发会话刷新
→ 聊天 HTTP 响应被捕获
→ 正确识别 incoming 方向、正文和时间
→ 重复刷新只写入一条 pdd_chat_messages
→ 工作台能够查看该回复
```

闭环稳定后进入 R1 工单建设，再依次实施 R2、R3C 和 R4。R5 必须在人工流程积累足够样本后单独评审。
