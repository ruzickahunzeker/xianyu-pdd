# 订单履约接口说明

本文档说明当前订单履约已经实现的 HTTP 接口，适用于管理后台、定时脚本及人工审核工具。

## 1. 基本约定

- 本地服务地址：`http://127.0.0.1:59188`
- 数据格式：除登录接口外，请求和响应均使用 JSON。
- 字符编码：UTF-8。
- 时间字段：Unix 秒级时间戳；`0` 表示尚未发生。
- 订单履约接口使用独立 Bearer 密钥，不使用浏览器 Cookie。
- 履约密钥只允许访问履约模块，不能访问账号、商品或管理员接口。
- 地址预览只操作本系统数据库；地址修改接口会修改配置的拼多多默认地址，但不会自动下单或付款。

密钥缺失或无效时返回：

```http
HTTP/1.1 401 Unauthorized

{"detail":"履约密钥无效"}
```

### 创建履约密钥

创建、查看和吊销密钥属于管理操作，仍需先登录管理后台。订单脚本本身不需要登录 Cookie。创建密钥：

```bash
curl -c admin-cookies.txt \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"请替换为实际密码"}' \
  http://127.0.0.1:59188/login

curl -b admin-cookies.txt \
  -H 'Content-Type: application/json' \
  -d '{"name":"订单履约脚本"}' \
  http://127.0.0.1:59188/api/fulfillment/keys
```

创建成功时，`api_key` 明文只返回一次：

```json
{
  "id": "2da3942d-4c54-48bd-94f4-f95cf3e894c8",
  "name": "订单履约脚本",
  "api_key": "xyf_请保存这里返回的完整密钥",
  "created_at": 1786700000
}
```

保存到脚本环境变量，后续履约请求只使用密钥：

```bash
export FULFILLMENT_API_KEY='xyf_请替换为实际密钥'

curl -H "Authorization: Bearer $FULFILLMENT_API_KEY" \
  http://127.0.0.1:59188/api/fulfillment/orders
```

数据库只保存密钥的 SHA-256 哈希，无法从数据库恢复明文。密钥丢失后应吊销旧密钥并重新创建。请勿把真实密钥、密码、收件人手机号或地址提交到 GitHub。

查看当前用户的密钥列表（不会返回密钥明文）：

```bash
curl -b admin-cookies.txt \
  http://127.0.0.1:59188/api/fulfillment/keys
```

吊销密钥：

```bash
curl -b admin-cookies.txt -X DELETE \
  http://127.0.0.1:59188/api/fulfillment/keys/2da3942d-4c54-48bd-94f4-f95cf3e894c8
```

## 2. 推荐调用流程

订单主数据和履约数据是两层独立数据：

1. 调用闲鱼订单同步接口，将最新订单写入 `orders`。
2. 查询履约订单；查询接口会自动为有效订单创建或更新履约记录，并尝试反向绑定发布素材及拼多多 SKU。
3. 查询未下单订单。
4. 下单前生成地址预览，人工核对后调用地址修改接口。
5. 人工完成拼多多下单后，将履约状态更新为已下单。
6. 拼多多发货后，写入物流公司、快递单号和拼多多发货状态。
7. 闲鱼发货脚本完成后，更新闲鱼发货状态。
8. 完成提醒流程后，更新提醒状态。

示例：

```bash
# 1. 同步闲鱼订单
curl -H "Authorization: Bearer $FULFILLMENT_API_KEY" -X POST \
  http://127.0.0.1:59188/api/orders/refresh

# 2. 查询尚未在拼多多下单的订单（自动同步履约表并解析 SKU 映射）
curl -H "Authorization: Bearer $FULFILLMENT_API_KEY" \
  'http://127.0.0.1:59188/api/fulfillment/orders?pdd_ordered=false'
```

已取消订单不会进入或显示在履约列表中。`POST /api/fulfillment/reconcile` 保留为脚本主动对账接口，但普通查询不再要求提前调用它。

## 3. 履约对账

### `POST /api/fulfillment/reconcile`

将当前密钥所属用户的所有有效、未取消闲鱼订单写入履约表，同时执行：

- 更新订单账号和闲鱼商品 ID；
- 根据闲鱼系统发货状态同步 `xianyu_shipped`；
- 查找该闲鱼商品最近一次成功发布记录；
- 根据闲鱼订单规格匹配发布 SKU；
- 回填素材 SKU、拼多多 `goods_id`、拼多多 `sku_id` 和闲鱼 SKU ID。

请求体可以为空：

```bash
curl -H "Authorization: Bearer $FULFILLMENT_API_KEY" -X POST \
  http://127.0.0.1:59188/api/fulfillment/reconcile
```

成功响应：

```json
{
  "success": true,
  "updated": 2
}
```

`updated` 表示本次成功创建或更新的履约订单数量，并不表示有多少订单状态发生变化。

## 4. 查询履约订单

### `GET /api/fulfillment/orders`

最多返回当前用户最近更新的 500 条有效履约订单，按 `updated_at` 倒序排列。

### 4.1 查询参数

| 参数 | 可选值 | 说明 |
| --- | --- | --- |
| `pdd_ordered` | `true`、`false`、`1`、`0` | 是否已经在拼多多下单 |
| `pdd_shipped` | `true`、`false`、`1`、`0` | 拼多多订单是否已发货 |
| `xianyu_shipped` | `true`、`false`、`1`、`0` | 闲鱼订单是否已发货 |
| `reminded` | `true`、`false`、`1`、`0` | 是否已经完成提醒流程 |
| `mapping_status` | `pending`、`mapped`、`unmapped`、`ambiguous` | SKU 映射状态 |

多个参数之间是“并且”关系。例如，查询已经拼多多发货、但闲鱼尚未发货的订单：

```bash
curl -H "Authorization: Bearer $FULFILLMENT_API_KEY" \
  'http://127.0.0.1:59188/api/fulfillment/orders?pdd_shipped=true&xianyu_shipped=false'
```

查询两个未下单订单：

```bash
curl -H "Authorization: Bearer $FULFILLMENT_API_KEY" \
  'http://127.0.0.1:59188/api/fulfillment/orders?pdd_ordered=false'
```

布尔参数填写其他值时返回 `400`，例如：

```json
{
  "detail": "pdd_ordered 只支持 true、false、1 或 0"
}
```

### 4.2 成功响应

此接口直接返回 JSON 数组，不额外包装 `data` 字段：

```json

    "order_id": "3640123456789012345",
    "cookie_id": "830668906",
    "item_id": "1073844478604",
    "spec_name": "款式",
    "spec_value": "USB 转 Type-C",
    "receiver_name": "张三",
    "receiver_phone": "132****4040",
    "receiver_address": "北京市海淀区中关村大街1号",
    "receiver_city": "北京市",
    "material_id": 18,
    "material_sku_id": "ec6e44fd-9bca-4d66-b907-2eb03545e696",
    "source_goods_id": "678814196103",
    "source_sku_id": "1928995096086",
    "xianyu_sku_id": "86024a67-4d01-483b-83be-d3b05dd242d3",
    "mapping_status": "mapped",

    "address_match_status": "pending",
    "last_error": "",

  }

```

实际响应中的手机号和地址是订单原始数据。上例手机号使用星号只是文档脱敏示意。

### 4.3 字段说明

| 字段 | 说明 |
| --- | --- |
| `order_id` | 闲鱼订单 ID，也是履约记录唯一标识 |
| `cookie_id` | 闲鱼账号 ID |
| `item_id` | 闲鱼商品 ID |
| `spec_name` / `spec_value` | 闲鱼订单选择的规格 |
| `material_id` | 发布来源素材 ID；未绑定为 `0` |
| `material_sku_id` | 系统内部稳定素材 SKU ID |
| `source_goods_id` | 拼多多商品 `goods_id` |
| `source_sku_id` | 拼多多 SKU ID |
| `xianyu_sku_id` | 发布成功后闲鱼平台 SKU ID |
| `mapping_status` | SKU 反向映射状态 |
| `pdd_ordered` | 是否完成拼多多下单 |
| `pdd_order_id` | 拼多多订单 ID |
| `pdd_shipped` | 拼多多订单是否已发货 |
| `logistics_company` | 物流公司名称 |
| `tracking_number` | 快递单号 |
| `xianyu_shipped` | 闲鱼是否已发货 |
| `reminded` | 是否完成发货后提醒流程 |
| `phone_restore_due_at` | 应恢复正确手机号的时间；当前阶段可能为 `0` |
| `address_match_status` | 地址编码匹配状态 |
| `last_error` | 最近一次地址匹配或履约处理错误 |

SKU 映射状态含义：

- `pending`：尚未找到对应的成功发布记录，暂时无法映射。
- `mapped`：唯一匹配到素材 SKU 和拼多多 SKU。
- `unmapped`：存在发布记录，但订单规格无法匹配任何发布 SKU。
- `ambiguous`：订单规格同时匹配多个发布 SKU，必须人工处理，禁止自动下单。

## 5. 更新履约状态

### `PUT /api/fulfillment/orders/{order_id}`

只更新请求体中明确提供的字段；未提供字段保持不变。

可更新字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `pdd_ordered` | boolean | 是否完成拼多多下单 |
| `pdd_order_id` | string | 拼多多订单 ID |
| `pdd_shipped` | boolean | 拼多多是否发货 |
| `logistics_company` | string | 物流公司 |
| `tracking_number` | string | 快递单号 |
| `xianyu_shipped` | boolean | 闲鱼是否发货 |
| `reminded` | boolean | 是否完成提醒流程 |

拼多多下单完成后：

```bash
curl -H "Authorization: Bearer $FULFILLMENT_API_KEY" -X PUT \
  -H 'Content-Type: application/json' \
  -d '{"pdd_ordered":true,"pdd_order_id":"240814-123456789012345"}' \
  http://127.0.0.1:59188/api/fulfillment/orders/3640123456789012345
```

拼多多发货并取得快递单号后：

```bash
curl -H "Authorization: Bearer $FULFILLMENT_API_KEY" -X PUT \
  -H 'Content-Type: application/json' \
  -d '{"pdd_shipped":true,"logistics_company":"中通快递","tracking_number":"ZT1234567890"}' \
  http://127.0.0.1:59188/api/fulfillment/orders/3640123456789012345
```

闲鱼发货完成后：

```bash
curl -H "Authorization: Bearer $FULFILLMENT_API_KEY" -X PUT \
  -H 'Content-Type: application/json' \
  -d '{"xianyu_shipped":true}' \
  http://127.0.0.1:59188/api/fulfillment/orders/3640123456789012345
```

提醒完成后：

```bash
curl -H "Authorization: Bearer $FULFILLMENT_API_KEY" -X PUT \
  -H 'Content-Type: application/json' \
  -d '{"reminded":true}' \
  http://127.0.0.1:59188/api/fulfillment/orders/3640123456789012345
```

成功响应：

```json
{
  "success": true
}
```

将状态设置为 `true` 时，系统记录相应发生时间；重新设置为 `false` 时，相应时间清零。

当前阶段尚未强制状态顺序，因此调用方应遵守：

```text
拼多多已下单 → 拼多多已发货 → 闲鱼已发货 → 已提醒
```

## 6. 地址与临时手机号预览

### `POST /api/fulfillment/orders/{order_id}/address-preview`

根据闲鱼订单的收货地址匹配拼多多省、市、区编码，并生成临时手机号。

当前临时手机号规则：

- 原手机号必须是 11 位纯数字；
- 固定修改第 5 位数字；
- 修改后的数字一定与原数字不同；
- 正确手机号仍保留在闲鱼订单中，后续恢复不依赖逆向计算。

示例：

```bash
curl -H "Authorization: Bearer $FULFILLMENT_API_KEY" -X POST \
  http://127.0.0.1:59188/api/fulfillment/orders/3640123456789012345/address-preview
```

成功响应：

```json
{
  "success": true,
  "name": "张三",
  "original_phone": "13216514040",
  "temporary_phone": "13217514040",
  "province_id": "2",
  "province_name": "北京市",
  "city_id": "52",
  "city_name": "北京市",
  "district_id": "502",
  "district_name": "海淀区",
  "address": "中关村大街1号",
  "check_region": true
}
```

接口成功后，会把行政区编码、临时手机号和 `address_match_status=matched` 写入履约记录，但不会向拼多多发送请求。

### `POST /api/fulfillment/orders/{order_id}/pdd-address/apply`

向拼多多发送默认地址修改请求。推荐先在“系统设置 → 拼多多账号”保存 Cookie 和默认地址 ID；Cookie 使用系统数据密钥加密，`pdd_user_id` 会从 Cookie 自动解析。接口不使用会动态变化的 `anti-content`。

拼多多 Cookie、默认地址 ID 和 User-Agent 统一从“设置 → 拼多多账号”读取，不再使用 `.env` 凭证兜底。

每次业务操作必须使用新的幂等键；只有同一次业务操作的网络重试才能复用同一个键：

```bash
curl -X POST \
  -H "Authorization: Bearer $FULFILLMENT_API_KEY" \
  -H 'Idempotency-Key: xianyu-order-id-address-v1' \
  http://127.0.0.1:59188/api/fulfillment/orders/闲鱼订单ID/pdd-address/apply
```

建议幂等键格式为 `{order_id}-address-v{attempt}`，例如 `3313845698508005453-address-v2`。服务器会永久保留该键第一次操作的账号、地址 ID 和结果：

- `replayed=false`：本次已创建新操作，并实际调用了拼多多。
- `replayed=true`：本次未调用拼多多，只返回该幂等键首次执行的历史结果。

修改了系统设置中的 Cookie、默认地址 ID、User-Agent 或收货信息后，旧幂等键不会改用新配置。确认前一次状态为 `failed` 后，必须把 `v1` 改为 `v2` 等新键再次发起业务操作。`result_unknown` 不得换键重试，应先人工核对。

成功响应示例：

```json
{
  "success": true,
  "replayed": false,
  "operation_id": "02c303a8-ac7b-495a-9149-61614897e1e1",
  "order_id": "3313845698508005453",
  "status": "applied",
  "pdd_address_id": "60984097534",
  "pdd_account_id": "9262fda6-6422-44fb-998a-975c89aad634",
  "http_status": 200,
  "error": "",
  "created_at": 1786760974,
  "finished_at": 1786760975
}
```

HTTP 状态与业务状态：

| HTTP | `status` | 处理方式 |
| --- | --- | --- |
| `200` | `applied` | 地址已修改，可进入人工核对和下单 |
| `202` | `result_unknown` | 不得自动重试，先人工核对拼多多当前地址 |
| `409` | `processing` 或账号锁冲突 | 等待当前操作结束，不要并发下单 |
| `502` | `failed` | 根据 `error` 修正配置，再使用新幂等键重新操作 |

注意：响应中的 `http_status` 是拼多多上游响应码，不一定等于本系统返回给调用方的 HTTP 状态码。

只有 `processing`、`pending_ship` 且尚未回填 `pdd_order_id` 的订单允许执行。成功返回 `status=applied`；上游结果无法确认时返回 HTTP `202` 和 `status=result_unknown`，此时不得换新幂等键盲目重试，应人工核对拼多多地址。

同一拼多多账号同一时间只能保留一笔地址修改任务。修改成功后账号锁会保持到回填拼多多订单号；放弃下单时可人工释放：

```bash
curl -X DELETE \
  -H "Authorization: Bearer $FULFILLMENT_API_KEY" \
  http://127.0.0.1:59188/api/fulfillment/orders/闲鱼订单ID/pdd-address/lock
```

以下情况返回 `422`：

- 地址为空；
- 无法匹配拼多多行政区编码；
- 地址同时包含多个可能的行政区；
- 手机号不是 11 位纯数字。

失败示例：

```json
{
  "detail": "无法匹配拼多多省市区编码"
}
```

失败原因同时写入履约记录的 `last_error`，并将 `address_match_status` 设置为 `failed`。

## 7. 常见问题

### 7.1 返回“接口不存在”

说明当前运行的是旧镜像或旧二进制。重新编译并重启本地服务：

```bash
docker compose -f compose.local.yml up -d --build app
```

部署正确时，缺少密钥的请求应返回 `401`，而不是 `404`。

### 7.2 `/api/orders` 有数据，但履约列表为空

当前版本的履约查询会自动对账，无须先调用 `POST /api/fulfillment/reconcile`。请先确认订单不是已取消状态，然后直接查询：

```bash
curl -H "Authorization: Bearer $FULFILLMENT_API_KEY" \
  'http://127.0.0.1:59188/api/fulfillment/orders?pdd_ordered=false'
```

### 7.3 查询未下单订单没有筛选效果

请使用以下任一种格式：

```text
?pdd_ordered=false
?pdd_ordered=0
```

不要使用 `no`、`否`、`null` 等值。

### 7.4 `mapping_status` 不是 `mapped`

禁止自动下单。应先检查：

- 闲鱼订单的 `item_id` 是否对应系统成功发布的商品；
- 发布记录是否成功回填闲鱼 SKU；
- 订单 `spec_name/spec_value` 是否和发布规格一致；
- 素材 SKU 是否保留正确的拼多多 `goods_id + sku_id`。

### 7.5 返回“履约密钥无效”

检查请求头是否为完整的 Bearer 格式：

```bash
curl -H "Authorization: Bearer $FULFILLMENT_API_KEY" \
  http://127.0.0.1:59188/api/fulfillment/orders
```

还需确认密钥以 `xyf_` 开头、没有多余空格，并且未被吊销。网页登录 Cookie 不能代替履约密钥。

### 7.6 修改默认地址 ID 后，响应仍是旧 ID

检查响应的 `replayed`。如果是 `true`，说明调用方复用了旧幂等键，服务器没有重新读取账号配置，也没有再次调用拼多多。前一次明确失败时，换用新幂等键：

```bash
curl -X POST \
  -H "Authorization: Bearer $FULFILLMENT_API_KEY" \
  -H 'Idempotency-Key: 3313845698508005453-address-v2' \
  http://127.0.0.1:59188/api/fulfillment/orders/3313845698508005453/pdd-address/apply
```

新请求应返回 `replayed=false`，且 `pdd_address_id` 应为当前设置中的默认地址 ID。

### 7.7 拼多多地址修改返回 HTTP 403

首先确认请求不是幂等回放，然后检查：

- Cookie 是否已过期；
- Cookie 中的 `pdd_user_id` 是否属于当前拼多多账号；
- 默认地址 ID 是否属于同一账号；
- User-Agent 是否与获取 Cookie 时的浏览器基本一致。

本接口不需要 `anti-content`。

- 单个拼多多账号的 Cookie 和默认地址 ID 配置；
- 真实修改拼多多默认地址；
- 地址修改幂等审计和账号级串行锁。

尚未实现：

- 浏览器自动点击创建拼多多待付款订单（接口和状态机已就绪，仍需真实页面联调）；
- 自动付款（明确保持人工审核）；
- 自动同步拼多多物流；
- 自动调用闲鱼发货；
- 发货一天后自动恢复手机号及执行客服提醒。

## 9. 采购任务接口（P0–P3）

领取指定闲鱼订单；不传 `order_id` 时领取最早一笔可采购订单：

```bash
curl -X POST -H "Authorization: Bearer $FULFILLMENT_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"order_id":"闲鱼订单ID","worker_id":"pdd-worker-1","lease_seconds":120}' \
  http://127.0.0.1:59188/api/fulfillment/purchase-tasks/claim
```

响应中的 `lease_token` 只在领取时返回。worker 必须保存它，用于续租、保存创单前基线、回传结果或中止任务。同一拼多多账号只能存在一笔活动任务；`submitting_unpaid_order` 和 `result_unknown` 不会因租约过期自动重领。

续租并推进步骤状态：

```bash
curl -X POST -H "Authorization: Bearer $FULFILLMENT_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"lease_token":"领取响应中的令牌","status":"browser_preparing","lease_seconds":120}' \
  http://127.0.0.1:59188/api/fulfillment/purchase-tasks/任务ID/heartbeat
```

将待付款页面原始 HTML 保存为创单前基线：

```bash
curl -X POST -H "Authorization: Bearer $FULFILLMENT_API_KEY" \
  -H 'Content-Type: text/html' --data-binary @orders-before.html \
  'http://127.0.0.1:59188/api/fulfillment/purchase-tasks/任务ID/unpaid-snapshot?phase=before&lease_token=领取响应中的令牌'
```

创单后再次提交页面（不带 `phase=before`），响应会返回 `candidates` 和 `candidate_count`。只有候选唯一并且订单详情的收货人、省市区、详细地址也已核对时，才可调用 `browser-result`：

```bash
curl -X POST -H "Authorization: Bearer $FULFILLMENT_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"lease_token":"令牌","status":"unpaid_order_created","before_order_sns":["旧订单号"],"pdd_order":{"order_id":"新拼多多订单号","goods_id":"goods_id","sku_id":"sku_id","quantity":1,"amount_cent":1090,"receiver_name":"张三","province":"北京市","city":"北京市","district":"海淀区","detail_address":"中关村大街1号"}}' \
  http://127.0.0.1:59188/api/fulfillment/purchase-tasks/任务ID/browser-result
```

服务端会再次核对 `goods_id + sku_id + quantity`、收货人和标准化地址，并强制最低利润 50 分。手机号不参与匹配。通过后只回填待付款 `pdd_order_id`，不会提前标记为已下单。

人工在拼多多付款并确认订单进入待发货后：

```bash
curl -X POST -H "Authorization: Bearer $FULFILLMENT_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"pdd_order_id":"拼多多订单号"}' \
  http://127.0.0.1:59188/api/fulfillment/purchase-tasks/任务ID/confirm-payment
```

### 9.1 启动 Docker 采购 worker

在本机 `.env` 配置设置页面创建的 `FULFILLMENT_API_KEY`。worker 使用现有 `DATABASE_URL` 和 `XIANYU_DATA_KEY` 读取并解密采购任务所绑定的拼多多账号，不再配置 `PDD_COOKIE`。首次必须保持只读模式：

```dotenv
PDD_PURCHASE_SUBMIT=false
PDD_HEADLESS=true
```

重新构建并运行一次只读验证：

```bash
docker compose -f compose.local.yml build app
docker compose -f compose.local.yml --profile pdd-worker run --rm \
  -e PDD_WORKER_ONCE=true pdd-worker
```

只读验证会打开待付款列表和结算页，保存基线，修改当前配置的拼多多地址，并核对收货人、省市区、详细地址、数量、唯一结算金额和最低 0.5 元利润，但不会点击“立即支付”。截图写入 `data/pdd-screenshots/`。

真实页面联调确认无误后，才显式启用创单：

```dotenv
PDD_PURCHASE_SUBMIT=true
```

worker 点击“立即支付”仅创建待付款订单，不进行付款。它会重新读取待付款列表，使用创单前后差集、`goods_id + sku_id + quantity + order_time` 唯一识别新订单，再打开订单详情核对姓名和地址。任何不唯一、登录失效、验证码、地址或利润不匹配都会停止当前账号队列并留下异常任务；不会按列表第一条猜测绑定。

## 10. 拼多多商家消息任务

消息任务与采购任务共用设置中保存的拼多多 Cookie、履约密钥及账号写锁，不需要维护第二份 Cookie。默认仅允许人工确认；“系统设置 → 拼多多消息真实发送”默认关闭。

```http
GET  /api/pdd/messages?status=awaiting_confirmation
POST /api/pdd/messages
POST /api/pdd/messages/{task_id}/confirm
POST /api/pdd/messages/{task_id}/cancel
POST /api/pdd/messages/{task_id}/retry
```

创建任务必须提供 `Idempotency-Key`、`goods_id`、消息类型和最终消息正文。`mall_sn` 可以显式提供，也可以按 `goods_id` 从采集商品中读取：

```bash
curl -X POST \
  -H "Authorization: Bearer $FULFILLMENT_API_KEY" \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: custom-message:977731220380:1' \
  -d '{"goods_id":"977731220380","task_type":"custom_message","message":"您好，请问什么时候发货？","send_mode":"manual_confirm"}' \
  http://127.0.0.1:59188/api/pdd/messages
```

Worker 内部使用同一组认证接口领取、心跳、提交预检和回填结果。预检不会填写或发送消息。任务进入 `awaiting_confirmation` 后，管理员确认才会进入发送队列。明确未点击的 `failed` 可以安全重试；`result_unknown` 可能已经发送，接口会禁止重试，必须人工核验。
