# 拼多多涨价自动同步闲鱼售价规划

## 1. 目标

当拼多多商品 SKU 的有效采购价上涨后，系统根据素材中保存的价格策略，找出所有绑定该拼多多 SKU 的闲鱼已发布 SKU，计算建议售价，并在满足安全条件时修改闲鱼售价。

系统必须形成完整闭环：

```text
拼多多商品更新
  → 识别可信价格变化
  → 生成去重的涨价事件
  → 查找素材及已发布 SKU 映射
  → 计算建议售价和利润
  → 预检闲鱼商品及完整 SKU
  → 修改闲鱼售价
  → 回读确认
  → 更新本地记录与审计日志
```

首期只处理拼多多涨价。拼多多降价只记录和提醒，不自动降低闲鱼售价。

## 2. 已有基础

项目当前已经具备以下基础能力：

- `pdd_products`、`pdd_skus` 保存拼多多商品、SKU、价格、库存和采集时间。
- 素材 SKU 保存 `material_sku_id`、`source_goods_id`、`source_sku_id`、采购价和闲鱼售价。
- `material_publish_records` 记录素材发布到哪个闲鱼账号及商品。
- `material_publish_sku_mappings` 保存稳定映射：

```text
拼多多 goods_id + source_sku_id
  → material_sku_id
  → xianyu_sku_id
  → 闲鱼账号 + 闲鱼商品 itemId
```

- 素材已经支持手工售价、固定加价、百分比加价和目标毛利率策略。
- 闲鱼接口 `mtop.alibaba.idle.seller.pc.common.item.search` 可以读取商品状态及完整 SKU 列表。
- 闲鱼接口 `mtop.alibaba.idle.seller.pc.item.info.update` 可以提交完整 SKU 列表修改价格和库存。

现有的本地商品更新接口只更新本地数据库，不能替代远程闲鱼改价接口。

## 3. 范围和非目标

### 3.1 本期范围

- 检测拼多多 SKU 采购价上涨。
- 生成价格变化事件并防止重复处理。
- 计算建议闲鱼售价及预计利润。
- 支持人工确认改价。
- 支持用户明确开启后的自动改价。
- 支持同一个拼多多 SKU 发布到多个闲鱼商品、多个闲鱼账号。
- 改价后回读闲鱼实际价格并记录结果。
- 对账号失效、映射缺失、风控、结果未知等异常安全停止。

### 3.2 本期不做

- 不自动跟随拼多多降价。
- 不根据规格文字猜测 SKU 映射。
- 不在定时发布、订单同步或履约过程中临时抓取拼多多价格。
- 不在拼多多风控降级、价格隐藏或解析不完整时改价。
- 不自动修改商品标题、描述、图片、规格名称或闲鱼原价。
- 不做常规库存镜像；只有可信精确库存低于10时触发安全收敛，其他改价请求保留平台当前库存。
- 不对失败的业务请求无限重试。
- 不实现任何拼多多商品定时轮询；价格和库存变化只由扩展采集、人工更新或采购前必要核验产生。

## 4. 可信价格变化判定

拼多多更新入口保持现有方式：

- 浏览器采集扩展提交完整商品数据。
- 商品与 SKU 页面点击“更新”，通过 Curl 更新。
- 后续可选的低频自动检查任务。

一次价格上涨必须同时满足：

1. 新旧记录属于同一 `goods_id + source_sku_id`。
2. 新采集时间晚于当前数据。
3. 新旧价格均大于零。
4. 新价格来自完整商品数据，不是风控降级页面、隐藏价或估算价。
5. 新采购价大于旧采购价。
6. 本次变化尚未生成过同一事件。

建议价格事件幂等指纹：

```text
SHA256(goods_id + source_sku_id + old_price_cent + new_price_cent + source_version)
```

如果 Curl 数据可信度不足，可要求连续两次结果一致才允许进入自动模式；采集扩展提交的完整原始数据可以直接进入候选事件。

## 5. 数据模型

### 5.1 拼多多价格变化事件

新增 `pdd_price_change_events`：

| 字段 | 说明 |
|---|---|
| `id` | 事件 ID |
| `user_id` | 用户 ID |
| `goods_id` | 拼多多商品 ID |
| `source_sku_id` | 拼多多 SKU ID |
| `old_price_cent` | 原采购价 |
| `new_price_cent` | 新采购价 |
| `source_type` | extension、curl、scheduled |
| `source_snapshot_id` | 对应采集快照 |
| `confidence` | exact、confirmed、degraded |
| `fingerprint` | 唯一幂等指纹 |
| `status` | detected、processed、ignored、invalid |
| `collected_at` | 数据采集时间 |
| `created_at` | 事件创建时间 |

只有 `exact` 或 `confirmed` 事件可以产生自动改价任务。

### 5.2 自动改价策略

新增 `material_reprice_policies`，按“素材 + 闲鱼账号”保存：

| 字段 | 说明 |
|---|---|
| `material_id` | 素材 ID |
| `account_id` | 闲鱼账号 ID |
| `mode` | off、notify、automatic |
| `price_mode` | manual、fixed_add、percent_add、margin、preserve_profit |
| `price_value` | 策略值 |
| `minimum_profit_cent` | 最低利润，默认严格大于30分 |
| `max_increase_cent` | 单次最大加价金额 |
| `max_increase_percent` | 单次最大涨幅 |
| `maximum_price_cent` | 最高允许售价 |
| `cooldown_seconds` | 同一闲鱼商品改价冷却时间 |
| `rounding_mode` | 分位取整、尾数 `.9`、尾数 `.99` 等 |
| `enabled` | 是否启用 |

按账号设置策略可以兼容同一素材发布到不同账号且售价策略不同的情况。

### 5.3 闲鱼改价任务

| `status` | 任务状态 |
| `idempotency_key` | 操作幂等键 |

| `request_json`、`response_json` | 审计数据，敏感字段脱敏 |
| `created_at`、`started_at`、`finished_at` | 时间字段 |

同一商品的多个 SKU 任务在执行阶段合并为一次远程更新请求。

## 6. 售价计算规则

### 6.1 固定加价

```text
目标售价 = 新采购价 + 固定金额
```

### 6.2 百分比加价

```text
目标售价 = 新采购价 × (1 + 加价比例)
```

### 6.3 目标毛利率

```text
目标售价 = 新采购价 ÷ (1 - 目标毛利率)
```

### 6.4 保持原绝对利润

```text
原利润 = 当前闲鱼售价 - 原采购价
目标售价 = 新采购价 + 原利润
```

### 6.5 手工售价

手工售价模式默认只生成提醒，不自动修改。

所有模式计算完成后必须再次检查：

- `目标售价 - 新采购价 > minimum_profit_cent`
- 不超过单次最大涨价金额。
- 不超过单次最大涨幅。
- 不超过最高售价。
- 符合价格取整规则。

不满足时任务进入 `blocked`，不得静默使用其他价格。

## 7. SKU 映射和多发布兼容

系统通过稳定 ID 查找受影响商品：

```text
pdd_price_change_events.goods_id + source_sku_id
  → material_publish_sku_mappings.source_goods_id + source_sku_id
  → material_publish_records
  → cookie_id/account_id + published_item_id + xianyu_sku_id
```

允许一个价格事件影响：

- 同一素材发布出的多个闲鱼商品。
- 同一个闲鱼商品中的一个或多个 SKU。
- 不同闲鱼账号中的多个商品。

只有以下映射可执行自动改价：

- `mapping_status = mapped`
- `source_goods_id` 非空
- `source_sku_id` 非空
- `xianyu_sku_id` 非空
- 最近一次成功发布记录仍有效

`manual`、`placeholder`、`pending`、`unmapped` 映射只能提示人工处理。

规格名称只用于页面展示和异常提示，不参与自动匹配。

## 8. 闲鱼精简改价协议

捕获到的卖家工作台实际流程已经确认，后端只需要两个业务接口：

```text
mtop.alibaba.idle.seller.pc.item.info.update   写入完整 SKU 售价
mtop.alibaba.idle.seller.pc.common.item.search 回读商品和 SKU
```

以下浏览器请求不属于业务协议，后端无需模拟：

- `d-gm.mmstat.com/itemadmin-tabselling-pricepop-clk`：点击统计上报。
- `d-gm.mmstat.com/aes.1.1`：埋点和接口调用统计。
- 浏览器自动发出的 `OPTIONS`：跨域预检。

不引入浏览器自动化，不依赖完整商品编辑接口，也不提交标题、描述、图片、分类或发货地。

### 8.1 本地闲鱼 SKU 快照

每次 `item.search` 同步后，本地保存商品级快照：

- `account_id + item_id`
- 商品状态及是否包含 `updatePrice`
- 完整 SKU 数量
- 每个 `skuId` 的 `priceInCent` 和 `quantity`
- 规格文字和规格图片，仅用于展示与异常提示
- 快照获取时间和内容指纹

默认快照有效期为10分钟。以下情况即使未过期也视为无效：

- 平台 SKU 数量与最近发布映射数量不一致。
- 任意已映射 `xianyu_sku_id` 在快照中不存在。
- 快照不是在卖状态或不包含 `updatePrice` 操作。
- 商品刚完成发布、上下架、擦亮、人工编辑或其他价格任务。
- 上一次远程写操作处于 `applying`、`verifying` 或 `result_unknown`。
- 快照来源不完整、解析失败或所属账号不一致。

### 8.2 两种请求路径

#### 快照有效：两次请求

```text
读取本地完整 SKU 快照
  → item.info.update
  → item.search 回读确认
```

这是正常自动改价的默认路径。

#### 快照无效：三次请求

```text
item.search 刷新基线
  → item.info.update
  → item.search 回读确认
```

这是首次改价、快照过期或发现映射差异时的安全路径。

无论走哪条路径，写入后都必须回读；不能只凭更新接口返回成功认定完成。

### 8.3 基线预检

从快照或 `item.search` 响应验证：

1. 商品仍为在卖状态。
2. `itemOperationInfo.operateItemList` 包含 `updatePrice`。
3. `idleItemSkuList` 是该商品的完整 SKU 列表。
4. 本地全部目标 `xianyu_sku_id` 均能找到。
5. SKU ID 唯一，价格和库存均为合法值。
6. 当前平台价格与任务建立时的基线不存在未解释的变化。

如果发现人工改价：

- 重新计算仍满足策略和利润边界时，转入人工确认。
- 无法判断意图时标记 `blocked_manual_change`。
- 不允许静默覆盖人工修改。

### 8.4 构造完整 SKU 请求

复制完整快照中的全部 SKU：

- 只替换目标 SKU 的价格。
- 保留其他 SKU 的平台当前售价。
- 所有 SKU 的库存使用平台当前 `quantity`。
- 不使用素材库存或过期本地库存覆盖闲鱼库存。
- 多个目标 SKU 属于同一商品时合并为一次请求。

单位和格式必须统一：

```text
item.search 读取：priceInCent = 620（单位：分）
item.info.update 提交：price = "6.20"（单位：元，固定两位小数字符串）
```

金额计算全程使用整数分，最终提交时才格式化为元，禁止使用浮点数参与利润计算。

### 8.5 提交改价

调用：

```text
mtop.alibaba.idle.seller.pc.item.info.update
```

请求只包含两个业务字段：

```json
{
  "itemId": "1082475790228",
  "itemSkuListStr": "[{\"skuId\":6301117014554,\"quantity\":1000,\"price\":\"3.99\"},{\"skuId\":6301117014555,\"quantity\":1000,\"price\":\"6.20\"}]"
}
```

`itemSkuListStr` 必须包含该商品全部 SKU。禁止只提交被修改的 SKU，也禁止缺少 `quantity`。

### 8.6 回读确认

提交后调用一次 `item.search`，按 `account_id + itemId + skuId` 核对：

- 目标 SKU 的 `priceInCent` 等于目标值。
- 未修改 SKU 的价格与写入基线一致。
- 所有 SKU 仍然存在。
- SKU 数量及库存没有意外变化。

只有回读一致才能标记 `succeeded`，并原子更新：

- `material_publish_sku_mappings.published_price_cent`
- 本地闲鱼商品 SKU 当前售价和库存快照
- 新的商品级快照、内容指纹和获取时间
- 任务完成时间及脱敏审计信息

回读未立即看到新价格时，只允许一次短延迟回读；仍不一致则进入 `result_unknown`，不得再次调用写接口。

## 9. 状态机和恢复

```text
detected
  → pending_review（仅提醒或需要人工确认）
  → queued（允许自动执行）
  → validating
  → applying
  → verifying
  → succeeded
```

异常状态：

- `blocked`：映射、利润、商品状态或策略不满足。
- `failed`：平台明确返回失败。
- `result_unknown`：请求超时或连接中断，无法判断是否已经生效。
- `ignored`：用户忽略本次变化。
- `cancelled`：执行前取消。

对于 `result_unknown`：

1. 禁止立即重复提交更新。
2. 先执行一次 `item.search` 回读。
3. 已生效则标记成功。
4. 回读仍为旧价格时，保留人工重试入口；系统不自动重放写请求。
5. 回读出现部分 SKU 已修改或库存异常时，暂停该商品并要求人工处理。

账号未授权、风控或权限错误发生后，立即暂停该账号的后续自动改价任务。

## 10. 并发、频率和风控

- 使用 `account_id + item_id` 分布式/数据库锁，防止同一商品并发改价。
- 同一商品的多个 SKU 合并成一次请求。
- 同一账号不同商品之间随机间隔30～60秒。
- 单账号每小时最多自动修改20个商品，允许配置但不能无限制。
- 同一商品默认6小时内最多自动改价一次。
- 一个账号只运行一个远程写操作。
- 发布、擦亮、上下架和改价不得同时操作同一商品。
- 平台明确失败不自动重试。
- 网络结果未知时先回读，不盲目重放写请求。
- Cookie 更新沿用现有账号设置数据，不维护第二份 Cookie。

操作包括：

## 12. 通知规则

建议接入现有异常通知体系：

- 自动改价成功：默认不提醒，可在设置中开启汇总。
- 需要人工确认：提醒一次。
- 利润低于安全线：高优先级提醒。
- 映射丢失、商品状态异常：提醒一次并阻塞。
- 登录失效、风控、无权限：暂停账号并高优先级提醒。
- 同一错误去重，避免循环通知。

## 13. 分阶段实施

### P0：协议与基线验证

- 封装 `item.search` 商品和 SKU 解析。
- 封装 `item.info.update` 完整 SKU 更新。
- 建立带有效期和内容指纹的闲鱼商品 SKU 快照。
- 实现有效快照两次请求、失效快照三次请求两条路径。
- 实现分/元单位的强类型转换。
- 提交价格统一格式化为固定两位小数字符串。
- 实现单个商品人工改价。
- 实现改价后回读确认。
- 使用 Mock 响应覆盖多规格、不同库存和规格图片。

### P1：价格变化事件

- 比较 `pdd_skus` 更新前后价格。
- 区分可信、确认和降级数据。
- 建立价格事件表、唯一指纹和幂等处理。
- 只记录和展示，不修改闲鱼商品。

### P2：建议售价和人工执行

- 实现所有价格策略计算器。
- 增加价格变动工作台。
- 根据发布映射生成受影响任务。
- 支持单个及批量人工确认。
- 完成多商品、多账号兼容验证。

### P3：安全自动改价

- 按素材和账号增加自动改价开关。
- 加入最低利润、最大涨幅、最高售价和冷却时间。
- 增加账号队列、锁和限速。
- 增加账号级暂停及恢复。
- 默认关闭，用户主动开启后才运行。

### P4：明确取消定时检查

- 不实现拼多多商品价格或库存的定时轮询。
- 不允许自动改价模块自行访问拼多多商品页。
- 只消费扩展采集、人工更新和采购前必要核验产生的可信本地数据。
- 接受非主动更新期间价格与库存不会自动发现的时效边界。

## 17. 低库存联动边界

可信拼多多数据更新时，同时检测精确库存：

- 精确库存为1～9：闲鱼对应 SKU 应同步为实际库存。
- 精确库存为0：闲鱼对应 SKU 更新为0；素材开启“缺货时停用”时同时停用。
- 库存重新达到10以上：按素材库存策略恢复为镜像值、上限值或用户配置值。
- `≥1000`、页面封顶、缺少 `stock_exact` 等不确定库存不触发低库存覆盖。
- 价格和库存变化属于同一闲鱼商品时，合并为一次完整 SKU 更新请求。
- 低库存保护允许把手工/固定库存向下收敛，但库存恢复时不擅自抬高手工/固定库存。

## 18. 拼多多 Worker 与临时浏览器模型

主应用和轻量 Worker调度器可以常驻，但不能让 Chromium 或拼多多页面长期在线：

```text
出现明确任务
  → 常驻 Worker领取一个本地任务
  → 启动临时 Chromium/BrowserContext
  → 连续完成该任务全部步骤
  → 关闭页面和浏览器上下文
  → Chromium进程退出
  → Worker继续等待本地任务
```

边界如下：

- Worker空闲时只轮询本项目本地API，不访问拼多多。
- 每次只处理一个采购、物流或商家消息任务。
- 无任务时不启动 Chromium，也不执行兜底物流扫描。
- 下一任务创建新的 Chromium进程、浏览器上下文和页面。
- Cookie、账号站点、浏览器版本、语言、时区和基础设备特征保持稳定，不能每次随机指纹。
- 同一拼多多账号同时最多一个 Worker。
- 明确失败后立即关闭该任务浏览器；不可在同一浏览器环境内每5秒循环重试。
- 网络结果未知时保存恢复状态并关闭浏览器；下一次新浏览器只进入恢复流程，绝不能再次点击提交订单。
- Docker中的 Worker使用 `restart: unless-stopped`，但它的空闲常驻不代表拼多多浏览器在线。
- `PDD_WORKER_ONCE=true` 只保留给手工单次测试，生产默认关闭。

## 14. 测试计划

### 14.1 单元测试

- 固定加价、百分比、毛利率、保持利润计算。
- 金额取整和分/元转换。
- 最低利润、最大涨幅、最高售价边界。
- 价格事件去重和旧数据拒绝。
- 映射状态筛选。
- 完整 SKU 列表只修改目标价格。

### 14.2 数据映射测试

- 一个拼多多 SKU 对应一个闲鱼 SKU。
- 一个拼多多 SKU 对应多个闲鱼商品。
- 一个素材发布到多个闲鱼账号。
- 修改过闲鱼规格名称但稳定 ID 未变化。
- `manual`、`placeholder`、`unmapped` SKU 被阻止。
- 已删除或重新发布商品使用最新成功发布记录。

### 14.3 接口测试

- `item.search` 多页响应。
- 快照有效时不执行写前搜索，仅执行写入和回读。
- 快照过期、缺少 SKU、账号不一致时强制刷新基线。
- 在卖商品包含 `updatePrice`。
- 下架商品和不可改价商品被阻止。
- 写入参数包含商品全部 SKU、全部当前库存和固定两位小数价格。
- 统计上报、埋点和 `OPTIONS` 不进入后端业务流程。
- `item.info.update` 成功、业务失败、未授权和风控响应。
- 修改成功后的回读一致。
- 回读发现未修改 SKU 价格变化或库存变化时阻塞。
- 请求超时但实际已生效。
- 请求超时且未生效。

### 14.4 并发和恢复测试

- 同一商品多个涨价事件合并。
- 同一商品并发任务只能一个持锁执行。
- 同一事件重复投递不重复改价。
- 账号暂停后队列不继续执行。
- 人工改价发生在任务执行前时不被静默覆盖。

## 15. 验收标准

P0～P2完成后应达到：

1. 拼多多采购价上涨能生成唯一价格事件。
2. 系统能准确列出所有受影响的闲鱼账号、商品和 SKU。
3. 规格名称修改不影响映射，系统只使用稳定 ID。
4. 建议售价符合素材价格策略和安全利润要求。
5. 修改一个 SKU 不会改变其他 SKU 的价格和库存。
6. 改价结果以平台回读为准，不只依赖写接口响应。
7. 网络结果未知时不会重复提交。
8. 多账号、多商品场景不会交叉修改。
9. 有效快照走两次请求，失效快照走三次请求。
10. 后端不会发送 mmstat 埋点或浏览器 `OPTIONS` 请求。

P3完成后还应达到：

1. 自动改价默认关闭，只有用户主动开启才执行。
2. 账号级限速、冷却、暂停和恢复有效。
3. 风控、权限和映射异常不会循环重试。
4. 每次自动改价都有完整、可查询的审计记录。

## 16. 推荐落地顺序

优先完成 P0、P1、P2并使用人工确认模式运行一段时间。确认闲鱼接口、完整 SKU 更新、回读验证和多账号映射稳定后，再开放 P3 自动模式。

最重要的实施边界是：只有可信的拼多多价格、明确的稳定 SKU 映射、通过安全预检的闲鱼商品，三者同时满足时才允许自动改价。
