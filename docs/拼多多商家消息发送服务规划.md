# 拼多多商家消息发送服务规划

## 1. 目标与边界

本模块是独立的浏览器执行服务，只负责：接收消息任务、定位指定拼多多商家聊天、填写并发送消息、验证发送结果、保存审计记录。

当前使用场景包括修改/恢复收货手机号、催发货、物流询问和人工自定义消息。未来跨平台客服中继也调用同一接口，但本模块不分析闲鱼消息、不生成业务答案、不读取客服回复，也不直接修改订单履约结论。

## 2. 输入与商家定位

稳定定位字段：

- `pdd_account_id`：使用设置中保存的拼多多账号 Cookie。
- `goods_id`：拼多多商品 ID。
- `mall_sn`：拼多多商家标识，必须由采集数据保存。
- `captured_chat_url`：采集时的完整聊天链接，仅作为回退地址。

默认生成链接：

```text
https://mobile.pinduoduo.com/chat_detail.html?goods_id={goods_id}&mall_sn={mall_sn}&from=goods&page_from=101
```

不持久依赖 `_oak_rcto`、`refer_page_id`、`goods_options` 等动态追踪参数。简化链接无法进入正确会话时，才使用 `captured_chat_url`。

## 3. 通用创建接口

```http
POST /api/pdd/messages
Authorization: Bearer {FULFILLMENT_API_KEY}
Idempotency-Key: {业务幂等键}
Content-Type: application/json
```

```json
{
  "pdd_account_id": "account-id",
  "goods_id": "977731220380",
  "sku_id": "1932571528030",
  "mall_sn": "CgI2WRIIS0xJNU5SeWUa...",
  "task_type": "restore_phone",
  "business_id": "3316978992113078290",
  "xianyu_order_id": "3316978992113078290",
  "pdd_order_id": "260816-xxxxxxxx",
  "message": "您好，订单……的收货手机号需要恢复为……，麻烦协助处理，谢谢。",
  "send_mode": "manual_confirm",
  "scheduled_at": 0,
  "metadata": {}
}
```

浏览器只使用已经渲染完成的 `message`，手机号替换、模板选择和触发时间由上层业务决定。

## 4. 数据模型

新增 `pdd_message_tasks`：

```text
id, user_id, idempotency_key
pdd_account_id, goods_id, sku_id, mall_sn, captured_chat_url
task_type, business_id, xianyu_order_id, pdd_order_id
message_text, message_fingerprint, metadata_json
source_platform, source_conversation_id, source_message_id, parent_task_id
reply_expected, send_mode, priority, scheduled_at
status, worker_id, lease_token, lease_expires_at, attempts
sent_at, verified_at, last_error, result_json
created_at, updated_at
```

唯一约束：`user_id + idempotency_key`。

首期任务类型：

- `change_phone`
- `restore_phone`
- `custom_message`

预留：`urge_shipping`、`logistics_question`、`product_question`、`customer_question`。

## 5. 状态机

```text
pending → claimed → opening_chat → page_ready
        → awaiting_confirmation → sending → sent → verified
```

异常状态：

```text
mapping_missing, login_required, captcha_required, merchant_mismatch,
input_not_found, send_button_not_found, result_unknown, failed, cancelled
```

`result_unknown` 表示已经点击发送但无法确认结果。该状态禁止直接重发，必须重新读取聊天记录并查找相同消息。

## 6. 浏览器执行流程

1. 领取任务并获取账号级租约。
2. 使用任务绑定的拼多多账号，不允许回退到其他默认账号。
3. 获取账号写锁和 `mall_sn` 商家锁。
4. 打开简化聊天链接；失败时回退采集链接。
5. 检查登录页、验证码、风控页和商家身份。
6. 定位 `textarea#input-content`，回退 `textarea.input-content`。
7. `manual_confirm` 模式先停在 `awaiting_confirmation`；确认后才填写和发送。
8. 填入消息后回读 textarea，必须与目标正文一致。
9. 定位可见的 `div.send-button`，并确认文本为“发送”。
10. 点击后等待输入框清空，并在自己的消息区域查找本次正文。
11. 验证成功后置为 `verified`，记录时间、页面摘要与截图。

不得依赖随机 CSS 类名或 `data-active="before-red"`。

## 7. 幂等与恢复

推荐幂等键：

```text
change-phone:{pdd_order_id}:{temporary_phone}
restore-phone:{pdd_order_id}:{original_phone}
urge-shipping:{pdd_order_id}:{yyyy-mm-dd}
customer-question:{xianyu_message_id}
```

- 已存在 `pending/running`：返回原任务。
- 已存在 `verified`：返回原成功结果。
- 已存在 `result_unknown`：阻止新建和重发。
- 安全失败（未点击发送）可按限制重试。
- worker 重启后通过租约恢复，不创建新任务。

## 8. 并发控制

- 同一拼多多账号一次只执行一个浏览器写操作，地址修改、下单和发消息共用锁。
- 同一 `mall_sn` 一次只允许一个发送任务。
- 一个 Page 只处理一条任务。
- 只读物流同步不能复用正在输入消息的 Page。

## 9. 管理页面

新增“拼多多消息”工作台，提供待发送、待确认、发送中、结果待确认、失败、已发送和全部筛选。

支持：新建、编辑未发送消息、预览、确认发送、取消、安全重试、重新核验记录、标记人工完成、查看截图和日志。进入 `sending/sent/verified` 后禁止编辑正文。

## 10. 设置

- 启用拼多多消息任务
- 默认发送模式（默认人工确认）
- 扫描间隔（默认 10 秒）
- 单次任务数（默认 1）
- 最大安全重试次数（默认 2）
- 截图保留天数

## 11. 实施阶段与验收

### P0：数据与 API

保存 `mall_sn`，建立任务表以及创建、列表、取消、领取、心跳、确认、完成接口，实现状态机与幂等。

### P1：只读预检

打开聊天页，核对登录、商家、输入框和发送按钮，不填写、不发送。

### P2：填写与人工确认

生成预览、人工确认、填写 textarea，并保存发送前截图。

### P3：发送与验证

点击发送，验证输入框清空和新消息出现，实现结果未知保护、锁和重启恢复。

验收要求：不能串账号或串商家；相同幂等键不重复发送；点击后无法确认时绝不盲目重发；当前默认不自动发送真实消息。
